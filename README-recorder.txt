Without the helper, open twitch-auto-recorder.html as a file:// tab-capture app.
Tab capture keeps the original display stream (hidden muted <video>); video tracks are not stopped until Disarm. Chrome must keep the shared tab's video surface. Unmute the Twitch player. Helper/streamlink is preferred (pulls the actual stream, no tab share).
Helper recordings: ~/TwitchRecordings  (localhost only, 127.0.0.1:8765)
Helper also lists ~/TwitchRecordings via GET /api/files (History merge) and retries early streamlink failures.
Helper mid-stream auto-resume: if streamlink dies mid-broadcast, the supervisor starts a new timestamped segment under ~/TwitchRecordings while recording is still wanted.
Helper mid-stream stall resume: if the output file stops growing for 90s while streamlink is still alive, the supervisor kills it and starts a new timestamped segment (same path as mid-stream exit).
Helper mid-resume give-up: after consecutive establish failures (or sooner when streamlink stderr says offline), the supervisor stops retrying so a closed recorder page cannot leave forever-retrying orphans. Auto-Rec can POST /api/record again if the stream is still live. Streamlink stderr snippets are attached to lastError.
Helper disk guard: /api/health reports free space on the recordings volume; warns below 2 GB free, refuses new /api/record below 512 MB, and mid-stream/mid-resume supervisors stop with a clear lastError instead of filling the disk.
Level meters (v6.7): every active rec card shows a multi-bar VU — tab-capture from AnalyserNode frequency data; helper from write-rate (bps) and optional ffmpeg peak/level on /api/status.
Helper drop/reconnect (v6.8): if the local helper vanishes after it was connected, the UI notifies once (names any ACTIVE recordings) and refreshes arm/status. When it returns with streamlink, Auto-Rec for currently-live streamers is kicked immediately — no waiting for the next Twitch poll tick.
Helper downloads (v6.9): open http://127.0.0.1:8765/api/download/filename.ogg (History Download buttons use the same URL; large files stay out of chat).
Stale lastErrors (v6.9): offline streamer misses are muted/dismissable and auto-hide when another streamer is actively recording; Clear posts /api/errors/clear. LAST_ERROR also clears when that username establishes successfully.
Batched Helix live poll (v6.10): one GET /streams tick for all streamers (chunked at 100 user_login), then parallel Auto-Rec starts via Promise.allSettled so later streamers are not blocked by earlier Helix calls or ~8s helper POSTs; stale Helix 401 clears token and retries once.
Helix rate-limit / transient resilience (v6.11): twitchGet waits on HTTP 429/503 (Retry-After, capped ~12s) and retries once after the existing 401 clear+retry; clear status in the error if still failing. Skipped-poll catch-up: when a Worker tick arrives while pollAll is in flight, pollQueued schedules one immediate follow-up instead of dropping the tick.

Mid-stream segment handoff (v6.14): finished mid-resume segments auto-merge into History with Download (on resume success and after Stop); unique output paths so --force never clobbers a prior segment; tiny failed-establish leftovers are scrubbed; in-progress files return 409 / show Recording… instead of a truncated download; rec-card timer uses session start (does not reset on resume) and shows seg N.
Auto-Rec after mid-resume give-up (v6.15): when the helper supervisor gives up mid-resume, finished segments merge into History immediately and Auto-Rec POSTs /api/record again right away if the streamer is still marked live (no waiting for the next Helix poll). Each poll also awaits a fresh helper /api/status before start/stop decisions so a give-up that landed during the Helix round-trip cannot leave ACTIVE stale and delay the restart.

After stream ends → remove voice → split → send to Drive (v6.36): Recorder Settings has a global toggle "After stream ends: remove voice → split → send to Drive" and each streamer has a "→ Drive" switch (both default on, stored in the same twitch-auto-recorder-v4 key; the helper also keeps them in ~/TwitchRecordings/.drive-pipeline.json so it works with the page closed). Only when a recording finalizes (Stop, stream ended, or mid-resume give-up — never the growing file) the helper queues one Music-only job for the whole session on the shared one-at-a-time Demucs queue: every segment is cut into ~10-minute FLAC chunks, run through Demucs, joined and encoded to <first segment>-music.ogg (Vorbis q6, 44.1 kHz stereo; an existing -music is reused for single-segment sessions). It waits while disk space is low. The full -music.ogg is kept; it is then cut with -c copy into equal parts: count = ceil(size / 45 MB), but parts are never shorter than 10 minutes unless that would push a part to 50 MB or more (then re-cut with one more part). Parts are named <base>-music-partNofM.ogg (a 4-hour stream ≈ 7 parts of ~34 min) and saved in ~/TwitchRecordings/Drive parts/<base>/. If Google Drive for Desktop is found they are copied (temp file + rename) into the Drive target: your chosen folder (Convert → Google Drive → Auto-send → "Use this folder"), else a My Drive folder named "Twitch" / "TwitchRecordings" / "Twitch Recordings", else My Drive/Twitch Recordings/Music only (created). Status shows "Sent to Drive (N parts)"; without Drive it says "Waiting for Drive" and the helper checks every 60 s and sends automatically once Drive appears (failed sends retry after 5 min). History rows show a ☁ Sent / ⏳ Waiting / ⚠ failed badge, "Send to Drive now" and "Split for Drive" (works on any existing -music file). Browser notifications fire when parts are ready or sent. API: GET /api/pipeline/status, POST /api/pipeline/prefs {enabled, users, target}, POST /api/pipeline/split {name}, POST /api/pipeline/deliver {base?}; /api/record accepts afterStream. While the pipeline is on for a streamer, the browser's per-segment Auto Music only is skipped for that streamer (the helper does the whole session). The helper never restarts while a recording, a Demucs job or a Drive copy is active. macOS note: the helper runs as a background LaunchAgent, so macOS privacy can block it from the Google Drive folder ("Operation not permitted"); the job then shows the fix — System Settings → Privacy & Security → Full Disk Access → add the helper's python3 — and retries every 5 min.
Free local Drive parts after successful send (v6.37): After a delivery reaches status=sent (all parts copied into the Drive target), the helper removes ~/TwitchRecordings/Drive parts/<base>/ and logs bytes freed — the full -music.ogg in ~/TwitchRecordings is kept. Waiting / error / FDA-blocked deliveries keep local parts so retry and Send to Drive now still work. Re-split for Drive can recreate parts anytime. On helper startup, leftovers from already-sent deliveries (v6.36) are cleared the same way. History Delete (and Delete selected) with withSiblings also removes matching Drive parts/<native_stem>/; deleting a -music primary removes Drive parts/<music_base_stem>/ and counts those bytes in bytesFreed. Actively sending deliveries refuse delete with HTTP 409 for that base; removing parts for a waiting delivery drops that delivery entry so the UI does not claim parts are ready.
Send the original to Drive too (v6.38): Recorder Settings has "Send original to Drive" and each streamer has an "Original → Drive" switch (both default on; same twitch-auto-recorder-v4 key; also stored in ~/TwitchRecordings/.drive-pipeline.json). The moment a recording finalizes, each finished original is queued and copied as-is (any size, no 50 MB limit) into an Originals subfolder of the same Drive target the parts use (e.g. My Drive/Twitch/Originals/<name>.ogg) with temp file + rename, the same Waiting-for-Drive / 60 s check / 5-min retry and the same macOS Full Disk Access message. The voice-removal job waits until the originals are sent (or are waiting because Drive is missing, or failed; at most 30 min), then removes the voice and splits as before; parts still go flat into the target. The local original in ~/TwitchRecordings is never deleted or moved by the pipeline; the v6.37 cleanup only removes Drive parts/<base>/ after a successful parts send. The full -music.ogg stays local and is not copied to Drive (the parts already contain all of it). History rows show ☁ Original in Drive / ⏳ waiting / ⚠ failed and "Send original now" (or "Send original to Drive" on any older finished recording); files still recording are refused. No clobbering between computers (Mac + Windows backup): if Drive already has a file with the same name and size it counts as sent and is not copied again; if the name exists with a different size, this computer's copy is saved as <name>-<ComputerName>.ext instead of replacing it (same rule for parts, except a manual Re-split from this computer may replace its own parts). Windows: the helper detects Google Drive for Desktop on any drive letter whose root has "My Drive" / "Shared drives" (G: by default), %USERPROFILE%\Google Drive (with or without a My Drive folder inside) and %USERPROFILE%\My Drive; path checks are case-insensitive there, Demucs tries CUDA first when nvidia-smi exists (CPU fallback). API: POST /api/pipeline/original {name}; /api/pipeline/prefs accepts origEnabled, origUsers; /api/record accepts sendOriginal; /api/health adds driveOriginals.
Stream restarts (v6.42): when a streamer ends their broadcast and goes live again right away, Twitch can answer "no playable streams" for a minute or more while the new broadcast spins up. The helper used to give up after about a minute of that (streamlink exited quickly, code 1, file=0B) and the rest of the show was lost. Now, for a streamer with Auto-Rec armed (or when no recorder page has reported in since the helper started), it keeps retrying for 8 minutes after a recording ends or a start quick-fails, backing off to one try every 30 seconds. The card shows "waiting for <name> to come back ... helper keeps trying until <time>". If they come back, recording continues as the next segment of the same session (joined seamlessly, one voice-removal + Drive send). If not, it gives up at the deadline exactly as before (the page notices, joins segments, runs voice removal / Drive). While the helper is in that wait, the page no longer cancels it when Twitch flips the streamer to offline. Trade-off: the after-stream voice removal / Drive send starts up to 8 minutes later after a normal stream end. Streamers the page says are NOT armed keep the old quick give-up. /api/status active[] has graceUntil (epoch secs, 0 when not waiting); the Drive status file says "waiting for the stream to come back, until HH:MM". Env: TWITCH_RECORDER_RESTART_GRACE_SECS (default 480; 0 = old behavior).
Helper updates itself unattended when idle (v6.43): until now every release needed someone to click Check for updates → Install update in the page, so a helper on a computer nobody looked at stayed old (Silver Bullet sat on 6.36 and missed the v6.42 stream-restart fix). Now the helper checks GitHub about 2 minutes after it starts and then every 3 hours, with or without the page open. When a newer version is out and Settings → "Install helper updates automatically when idle" is on (default on; same twitch-auto-recorder-v4 key; also autoUpdate in ~/TwitchRecordings/.drive-pipeline.json) it waits until nothing is busy — no recording (including the v6.42 wait for a stream to come back), no voice-removal / split job running or queued, no seamless join, no Drive copy in flight or original queued for Drive, no upload arriving — and the helper has been idle for 5 minutes (so after-stream steps can queue), then installs it and restarts itself through the v6.32 deferred-safe restart. If anything starts while it installs, the restart waits again. Installs are safer for both the automatic and the manual path: all files are downloaded first and checked (the new helper must compile, its HELPER_VERSION must match VERSION, the HTML must be complete, and the new helper must pass a quick `--self-test` run in a temp folder); the current files are copied to <install dir>/.update-backup/ before the swap (BACKUP-INFO.txt says how to roll back), VERSION is written last, and if a write fails midway the backup is put back. A bad or partial download is never installed — the helper keeps running its current version and retries in 30 minutes; network errors also retry in 30 minutes. The idle restart after a manual install now uses the same busy rules and also runs with the page closed; a VERSION file that doesn't match the script no longer causes a restart loop. Helpers on 6.42 or older still need one last manual Check for updates → Install update (or: with the setting on, a page that sees an older helper idle for 2+ minutes and no streamer live does that install once per session); after that they update themselves. The update panel / Setup step 6 show "Auto-update: on · last checked … (up to date)", "v6.44 available, installs when idle (waiting: recording whistleface)" or the last error; the helper bar shows "⬆ v… installs when idle". The Drive status file (Recorder status/<computer>.txt + .json) gains a "Helper auto-update: on/OFF; last checked …" line and an autoUpdate object {enabled, state, lastCheckAt, lastResult, lastError, remoteVersion, waitingFor, lastAppliedVersion, lastAppliedAt} so the Friday/Sunday ready check can see it. API: /api/health.autoUpdate {enabled, state (up-to-date / waiting-idle / installing / restart-pending / restarting / error / off), lastCheckAt, lastResult, lastError, remoteVersion, waitingFor, nextCheckAt, lastAppliedVersion, backupDir, pendingRestart}; GET /api/update/auto; POST /api/update/auto {enabled?, checkNow?}; POST /api/pipeline/prefs accepts autoUpdate; GET /api/update/check also returns autoUpdate. Env: TWITCH_RECORDER_AUTO_UPDATE=0 (hard off), TWITCH_RECORDER_AUTO_UPDATE_FIRST_SECS (120), TWITCH_RECORDER_AUTO_UPDATE_SECS (10800), TWITCH_RECORDER_AUTO_UPDATE_RETRY_SECS (1800), TWITCH_RECORDER_AUTO_UPDATE_IDLE_SECS (300). Log lines start with "auto-update:".
Resume after-stream jobs after a helper restart (v6.44): voice removal runs for hours after a stream, and until now the job only lived in memory, so if the helper quit mid-job (crash, reboot, power blip, the computer killing it, a manual restart) that stream was never voice-removed, split or sent to Drive. Queued/running stream jobs are now saved as pendingJobs in ~/TwitchRecordings/.drive-pipeline.json and re-queued about 20 s after the helper starts again (the originals step and any existing -music file are reused, so nothing is redone needlessly). A job is dropped from the list when it finishes, is cancelled or errors; a job that keeps getting interrupted is retried at most 3 times, and jobs older than 3 days or whose recording is gone are skipped. Env: TWITCH_RECORDER_PIPELINE_RESUME_MAX (3), TWITCH_RECORDER_PIPELINE_RESUME_MAX_AGE_SECS (259200), TWITCH_RECORDER_PIPELINE_RESUME_DELAY (20). Log lines start with "pipeline resume".

Local Recorder status mirror + sticky Drive-access banner (v6.47): when macOS Full Disk Access (or missing Drive for Desktop) blocks writing the Drive status file / sending parts, the Friday ready check and UI used to look like the computer was simply offline, or bury the error in the Convert pipeline box. Now, whenever "Post this computer's status to Drive" is on, the helper always writes the same status doc to ~/TwitchRecordings/Recorder status/<computer>.txt and .json (under the recordings folder — no Full Disk Access needed), using the same atomic temp+rename pattern as Drive, and still attempts the Drive write to <Drive target>/Recorder status/ as before. /api/health.statusFile tracks localLastWrittenAt / localTxtPath / localError separately from the Drive fields, plus driveOk; /api/health.driveAccess is {ok, error, kind: ok|fda|missing|other} so the page can show a sticky banner with FDA instructions (or "Drive not found") and one-shot flash+notify per blocked episode. The Drive status row shows Drive failed (red) alongside the local mirror path/ago when Drive is blocked. The plain-text status file mentions the local mirror path and any Drive write error on one clear line. Ready checks can read the local JSON when Drive is blocked.

Windows log text can no longer break Drive sends (v6.51): on Windows, when the helper's output goes to a log file or a pipe instead of a console window (started hidden with Start-Process / Task Scheduler / a launcher, and always during the auto-update self-test), Python writes it in the old Windows code page (cp1252) and fails on characters that page doesn't have. The "sent" log lines for Drive contain an arrow (→), so on such a computer every set of parts and every original that had just been copied into Drive was then marked "error" (History: Drive send failed: 'charmap' codec can't encode character '\u2192' …), the local Drive parts were never cleared, the one-copy note in Recorder status/Sent parts/ said "error" (so the other computers sent their own duplicate set) and the helper retried the same send every 5 min forever. A closed console or dead pipe was worse: the first log line raised and could stop the helper or a background loop outright. Now a log line can never fail the work it describes: characters the output can't show are written as \uXXXX, a log line that can't be written at all is dropped (and counted), and once every part / the original is in Drive nothing after that can turn the send into "error". ffprobe / ffmpeg / streamlink output is read as UTF-8 (unknown bytes replaced) instead of the Windows code page, so odd characters in tags or titles can't fail a voice-removal job or a live check. Sends already stuck in "error" this way fix themselves on the first retry after the update (the files are already in Drive with the same size, so nothing is copied twice; local parts are then cleared and the note becomes "sent"). No settings. API: /api/health.logWriteErrors (log lines that could not be written as-is) and /api/health.logEncoding. The self-test now runs a full parts + original send with a cp1252 output.

Stay awake before armed streamers' usual go-live times (v6.52): keep-awake (v6.40) only held sleep off once a recording had started, or (opt-in) while the recorder page was open with Auto-Rec armed. A Mac or PC left alone in the afternoon could idle-sleep before the evening stream and miss it completely — the v6.49 helper watch can't run on a sleeping computer. The helper already knows when each streamer usually goes live, because every recording is named <user>-<Wkd>-YYYY-MM-DDTHH-MM-SS. Unmute add-on — auto-unmute Twitch on Arm (v6.31)
-------------------------------------------------
Twitch often autoplay-mutes the player, which makes tab-capture audio silent. The recorder page cannot touch other tabs, so v6.31 ships a small Chrome (MV3) extension, "Twitch Auto-Recorder Unmute" (repo folder extension/, installed/packaged as twitch-unmute-extension).
When you click Arm (before and after the tab picker), and when the silence watchdog fires for an armed streamer (once per silence episode), the page asks the add-on to unmute that streamer. The add-on finds open tabs at twitch.tv/<username> (www./m., popout twitch.tv/popout/<username>/player, or player.twitch.tv/?channel=<username>; case-insensitive, query/hash ignored), clears Chrome's tab-level mute, and on the page: clicks Twitch's mute button when it shows "Unmute", sets the <video> unmuted, and raises volume 0 → 50%. It retries for ~10s while the player loads. You'll see "🔊 Unmuted Twitch for <name>". The recorder's own hidden keepalive <video> stays muted on purpose.

Install (Chrome / Edge / Brave):
  1) Get the folder: Mac installs put it at ~/Library/Application Support/TwitchRecorder/twitch-unmute-extension (install.sh copies it there), or unzip twitch-unmute-extension.zip, or use extension/ from the repo.
  2) Open chrome://extensions
  3) Turn on Developer mode (top-right toggle)
  4) Click "Load unpacked" and pick the twitch-unmute-extension folder
  5) Reload the recorder page (GitHub Pages or http://127.0.0.1:8765/). If you use the file:// HTML, also enable "Allow access to file URLs" on the add-on's Details page.

Limitations: only tabs whose URL is the streamer's channel page (twitch.tv/<username>) or the popout/player URLs above are matched — raids/host redirects to another channel or /videos pages are not. Chrome may block unmuting a muted-autoplay video without a click (autoplay policy); then the add-on keeps it playing muted and the UI asks you to click the Twitch tab and unmute manually. If the add-on isn't detected, Arm shows a one-time dismissable hint. Manual unmute always still works.

Twitch ad breaks no longer cut recordings or block starts (v6.57): streamlink 7 and newer always leave Twitch ads out of the recording, so during an ad break the file simply stops growing. Mid-roll breaks are often 90-180 s, longer than the 90 s "streamlink stalled" check, so the helper killed streamlink in the middle of the ad, started a new segment and lost a few seconds of the set at the cut (and the reconnect could hit a fresh pre-roll). A start that sat in a pre-roll ad wrote nothing for longer than the 20 s start check, so it was killed and retried, and each retry could get a new pre-roll. Now the helper reads streamlink's own log while the file isn't growing: while it says "Waiting for pre-roll ads to finish" or "Filtering out segments and pausing stream output" (and no "Resuming stream output" after it), the gap is an ad, not a hang. It waits for the reported ad length ("Detected advertisement break of N seconds") plus at least 90 s of slack, or up to 8 min when no length is given, then the normal stall / retry rules apply again. Streamlink is started with --loglevel info so those lines are always there. The rec card's level meter reads "ad break ~45s · not recorded" (or "pre-roll ad") instead of "stalled", and the helper log has "ad break:" / "ad break over:" lines. Ads are still not recorded, by design: the recording just skips that stretch. API: /api/status active[].adBreak {since, secs, preroll} and adBreaks (count this session); /api/health.adPause {maxSecs, breaks, prerolls, stallsAvoided, lastAt, lastUser, lastSecs}. Env: TWITCH_RECORDER_AD_PAUSE_MAX_SECS (480; 0 = old behavior).

Wake a sleeping Windows PC for the usual go-live (v6.58): v6.52 keeps the computer awake from about 2 hours before an armed streamer usually goes live, but only if it is still awake then. A PC that idle-slept overnight or in the afternoon stayed asleep through the stream (for example whistleface's Tuesday ~10 AM stream after a night of sleep) and recorded nothing, because nothing on a sleeping computer can run. On Windows the helper now registers one per-user Scheduled Task, "TwitchRecorderWakeForStream" (no admin needed), with "Wake the computer to run this task" turned on and one trigger at the start of each learned go-live window in the next 8 days (e.g. Tue 8:00 AM, Fri 4:49 PM; two windows less than 30 minutes apart share one wake). The task runs "pythonw twitch-recorder-server.py --wake", which resets Windows' idle timer, tells the helper it was woken (POST /api/keep-awake/wake) so the v6.52 keep-awake hold and the closed-page streamer check happen right away instead of Windows putting an unattended wake back to sleep after ~2 minutes, and starts the helper if it isn't running. The task is updated every 15 minutes when the learned times or the armed streamers change, and removed when there is nothing to wake for, when "…and before armed streamers' usual go-live times" is off, or with env TWITCH_RECORDER_WAKE_FOR_STREAM=0. Windows only wakes for it when the power plan allows wake timers (Power Options → Sleep → Allow wake timers → Enable); the helper reads that setting and shows a warning on the page and in the status file when it is off or set to "Important wake timers only" — it never changes it. A PC that is shut down (not asleep) can't be woken. macOS only lets an administrator schedule wakes (pmset), so a Mac like Silver Bullet still has to be kept from sleeping on stream days; the page and /api/health say so. The page shows the next wake next to the learned go-live windows; the Recorder status file gets a "Wakes from sleep for: …" line. API: /api/health.keepAwake.wake {supported, enabled, task, next, nextAt, registeredAt, error, wakeTimers (enabled / disabled / important-only), wakeTimersHint, lastWakeAt}; POST /api/keep-awake/wake. Env: TWITCH_RECORDER_WAKE_FOR_STREAM=0, TWITCH_RECORDER_WAKE_REFRESH_SECS (900). Log lines start with "wake:". The self-test covers the wake times, the task XML, register / unchanged / remove / Access is denied, the wake-timer setting and --wake starting a missing helper.

The helper sets up its own streamlink on a newer Python (v6.59): Twitch changes its site every few months and older streamlink releases then stop finding streams. The newest streamlink (8.x) needs Python 3.10 or newer, so a Mac whose only Python is the macOS Command Line Tools Python 3.9 (like Silver Bullet) was stuck on streamlink 7.6.0 for good; v6.55 could only say "install a newer Python". Now, when "Keep streamlink up to date when idle" is on and this computer's Python is too old for the newest streamlink, the helper builds its own copy once, when nothing is recording, removing voice or sending to Drive: a separate Python environment with the newest streamlink, in ~/.twitch-recorder/streamlink (Windows: %LOCALAPPDATA%\TwitchRecorder\streamlink). It uses a newer Python that is already on the computer when there is one (Homebrew, python.org, pyenv, Windows Python), and otherwise a standalone Python fetched with uv (Astral's Python installer; one download from GitHub, checked against its published SHA-256; no admin password and nothing installed system-wide; about 200 MB). The copy is only switched on after the same checks as a v6.55 upgrade (streamlink --version, the Twitch plugin handles twitch.tv, every option the recorder uses exists); a failed build is removed and retried after an hour, at most 3 times per streamlink release, and the old streamlink keeps working meanwhile. From then on the normal v6.55 updater keeps the copy current with pip. The helper itself keeps running on the same Python as before, so a Mac's Full Disk Access setting for Drive is not affected. If the copy ever stops working (for example Homebrew replaced the Python it was built on), the helper goes back to the system streamlink by itself and builds a new copy. The Settings line next to "Keep streamlink up to date when idle", the helper bar and the Recorder status file show "setting up streamlink 8.x on a newer Python…" and then "(helper's own copy, Python 3.12)". API: /api/health.streamlinkUpdate gains states private-waiting / private-building and private {active, dir, version, pythonVersion, how, builtAt}. Env: TWITCH_RECORDER_PRIVATE_STREAMLINK=0 (never build or use it), TWITCH_RECORDER_PRIVATE_STREAMLINK_DIR, TWITCH_RECORDER_PRIVATE_STREAMLINK_PYTHON (3.12). Log lines start with "streamlink update:" / "streamlink private copy:". The self-test covers the uv download names, switching to and away from the copy, waiting while busy, the 3-try limit, and both build routes, without building anything for real.
