Twitch Auto-Recorder v6.29

pip install streamlink
python twitch-recorder-server.py
# then open http://127.0.0.1:8765/

Without the helper, open twitch-auto-recorder.html as a file:// tab-capture app.
Tab capture keeps the original display stream (hidden muted <video>); video tracks are not stopped until Disarm. Chrome must keep the shared tab's video surface. Unmute the Twitch player. Helper/streamlink is preferred (pulls the actual stream, no tab share).
Helper recordings: ~/TwitchRecordings  (localhost only, 127.0.0.1:8765)
Helper also lists ~/TwitchRecordings via GET /api/files (History merge) and retries early streamlink failures.
Helper mid-stream auto-resume: if streamlink dies mid-broadcast, the supervisor starts a new timestamped segment under ~/TwitchRecordings while recording is still wanted.
Helper mid-stream stall resume: if the output file stops growing for 90s while streamlink is still alive, the supervisor kills it and starts a new timestamped segment (same path as mid-stream exit).
Helper mid-resume give-up: after consecutive establish failures (or sooner when streamlink stderr says offline), the supervisor stops retrying so a closed recorder page cannot leave forever-retrying orphans. Auto-Rec can POST /api/record again if the stream is still live. Streamlink stderr snippets are attached to lastError.
Helper disk guard: /api/health reports free space on the recordings volume; warns below 2 GB free, refuses new /api/record below 512 MB, and mid-stream/mid-resume supervisors stop with a clear lastError instead of filling the disk.
Level meters (v6.7): every active rec card shows a multi-bar VU — tab-capture from AnalyserNode frequency data; helper from write-rate (bps) and optional ffmpeg peak/level on /api/status.
Helper drop/reconnect (v6.8): if the local helper vanishes after it was connected, the UI notifies once (names any ACTIVE recordings) and refreshes arm/status. When it returns with streamlink, Auto-Rec for currently-live streamers is kicked immediately — no waiting for the next Twitch poll tick.
Helper downloads (v6.9): open http://127.0.0.1:8765/api/download/filename.ogg (History Download buttons use the same URL; large files stay out of chat).
Stale lastErrors (v6.9): offline streamer misses are muted/dismissable and auto-hide when another streamer is actively recording; Clear posts /api/errors/clear. LAST_ERROR also clears when that username establishes successfully.
Batched Helix live poll (v6.10): one GET /streams tick for all streamers (chunked at 100 user_login), then parallel Auto-Rec starts via Promise.allSettled so later streamers are not blocked by earlier Helix calls or ~8s helper POSTs; stale Helix 401 clears token and retries once.
Helix rate-limit / transient resilience (v6.11): twitchGet waits on HTTP 429/503 (Retry-After, capped ~12s) and retries once after the existing 401 clear+retry; clear status in the error if still failing. Skipped-poll catch-up: when a Worker tick arrives while pollAll is in flight, pollQueued schedules one immediate follow-up instead of dropping the tick.
Filenames include weekday: username-Tue-2026-09-15T10-08-45.ogg
Mid-stream segment handoff (v6.14): finished mid-resume segments auto-merge into History with Download (on resume success and after Stop); unique output paths so --force never clobbers a prior segment; tiny failed-establish leftovers are scrubbed; in-progress files return 409 / show Recording… instead of a truncated download; rec-card timer uses session start (does not reset on resume) and shows seg N.
Auto-Rec after mid-resume give-up (v6.15): when the helper supervisor gives up mid-resume, finished segments merge into History immediately and Auto-Rec POSTs /api/record again right away if the streamer is still marked live (no waiting for the next Helix poll). Each poll also awaits a fresh helper /api/status before start/stop decisions so a give-up that landed during the Helix round-trip cannot leave ACTIVE stale and delay the restart.
Helper status Worker (v6.16): /api/health+/api/status no longer depends on a page setInterval (Chrome throttles those hard in background tabs). A dedicated Worker ticks every 2s so mid-resume give-up detection, Auto-Rec restart kicks, and helper reconnect stay timely while the recorder tab is backgrounded; overlapping pings are serialized; becoming visible always refreshes helper status (even if Helix is disconnected).
Helper Music only (v6.17): History rows for finished helper/disk files get a Music only button. POST /api/music-only starts a background demucs job (--two-stems=vocals, keep no_vocals); GET /api/music-only/<jobId> polls status. Output is saved next to the original as <name>-music.mp3 (or .m4a/.wav). /api/health reports demucs true/false. Install: pip install demucs (first run downloads models; needs ffmpeg for compact mp3/m4a).
Helper Music keep-both + Redo (v6.18): native recording is never overwritten or deleted. Music only writes a sibling <stem>-music.mp3 (m4a/wav fallback) and, when demucs already produced it, also <stem>-vocals.mp3. POST /api/music-only accepts { "name", "redo": true|false }; redo false/omitted returns already:true if -music exists; redo true replaces prior -music/-vocals and re-runs. History shows Download (native), Download music / Download vocals when present, and a Redo checkbox beside Music only / Music ready / Redo music. Install: pip install demucs.
Music job resume via health (v6.19): /api/health includes musicJobs (queued/running plus done/error kept ~15 min) and helper version. The HTML Worker health path merges those jobs so a backgrounded or refreshed page still shows Music… progress and fires desktop notify + Download once on Done/Error (notified jobIds are tracked so reconnect spam does not re-notify). Starting Music only while a job for the same native file is already queued/running returns alreadyRunning and reattaches instead of spawning a second demucs. Native recording is never deleted. POST /api/music-only + Redo (v6.18) unchanged.
Seamless recordings (v6.20): Settings toggle Seamless recordings (default on, persist key v4). When a mid-stream multi-segment session stops or mid-resume gives up, the helper joins finished segments via ffmpeg concat into <firstStem>-seamless.<ext> next to ~/TwitchRecordings — native segment files are never deleted. POST /api/seamless with { "names": [...] } or { "username" }; GET /api/seamless/<jobId>; /api/health exposes ffmpeg, seamless, seamlessJobs. History shows Join seamless for 2+ related finished segments. Requires ffmpeg.
Music only upload (v6.20): History Upload for Music only — multipart POST /api/music-only-upload saves under ~/TwitchRecordings (unique name on collision) and starts the same Demucs pipeline as /api/music-only. Reuses musicJobs / health reattach / notify / Download music+vocals / Redo. Existing History Music only on disk files unchanged. Max 4 GB; requires demucs.
Music only progress meter (v6.21): helper streams demucs stdout/stderr line-by-line, parses tqdm XX% into job progressPct (phases: queued/prepare 0–5, demucs ~5–88, encode instrumental ~90, vocals ~95, done 100). GET /api/music-only/<id> and /api/health musicJobs expose progressPct; History + Upload for Music only show a purple progress bar and percent. Upload XHR also reports bytes-sent before switching to conversion meter. Files still land in ~/TwitchRecordings as <name> then <stem>-music / -vocals. Seamless join jobs reuse the same meter style with coarse progressPct.
Convert tab (v6.22): Music only upload + progress meter moved to a top-level Convert tab next to History (History keeps per-row Music only / Redo).
Auto Music only (v6.23): Recorder Settings toggle (default on, persist key v4 as autoMusicOnly). Native streamlink recording is unchanged; each finished helper segment (mid-stream handoff, Stop / Stop All, or mid-resume give-up) auto-queues the same Demucs Music only job as History (redo:false) so `-music` / `-vocals` siblings appear while the next segment may still record. Never overwrites natives; never runs Demucs on the still-growing active file (helper 409 if still ACTIVE). Needs demucs; not true real-time stem separation — no live demucs-in-streamlink pipeline (too heavy / unreliable).
Graceful demucs-missing UX (v6.24): when /api/health reports demucs:false, Auto Music only soft-skips finished segments (no failed-job spam); one-shot flash + desktop notify + sticky banner explain `pip install demucs` and helper restart; helper bar shows "demucs missing"; History shows "Need demucs" instead of a clickable Music only; Convert Upload is disabled with the same hint. When demucs becomes true again, banner clears and Music only resumes. Native recordings unchanged.
GitHub auto-update (v6.25): GET /api/update/check compares local HELPER_VERSION / VERSION to the public repo `ewanders1-web/twitch-auto-recorder` (raw main). POST /api/update downloads `twitch-auto-recorder.html`, `twitch-recorder-server.py`, `README-recorder.txt`, and `VERSION` into the install dir (same folder as the running server — Application Support when installed) via atomic temp+replace. Never self-kills; always returns needsRestart:true (leaves ACTIVE recordings running). UI: Check for updates on the helper bar / API Setup; Install update confirms via flash + button. After install: restart helper (Desktop launcher / LaunchAgent) + hard-refresh the page. /api/health includes updateRepo.
Home streamer / return after set (v6.25): persist `homeStreamer` + `returnHomeAfterSet` (default true) under localStorage key v4. Streamers tab ★ Home (one only, clearable) + Return home after set toggle. When a non-home streamer goes live→offline (guest/DJ set ended) — including after helper/tab stop on Helix offline — if home is set, live, Auto-Rec on, and not already recording, Auto-Rec starts home (`startRec(home, true)`) with flash/notify "Returning to home streamer <name>". Does not steal focus while home is already recording; does not start home if offline. Mid-resume give-up on a non-home streamer still triggers return-home once Helix marks them offline.

GitHub Pages + portable install (v6.26): Open the UI from https://ewanders1-web.github.io/twitch-auto-recorder/ on any browser/computer. Recording still requires the Python helper on the machine that should save files (streamlink → ~/TwitchRecordings). Pages cannot record by itself. Helper keeps Access-Control-Allow-Origin: * so Pages → http://127.0.0.1:8765 works when the helper runs on that same machine (localhost only — never bind 0.0.0.0). Install helper: curl -fsSL https://raw.githubusercontent.com/ewanders1-web/twitch-auto-recorder/main/install.sh | bash  (macOS → ~/Library/Application Support/TwitchRecorder; Linux → ~/.local/share/TwitchRecorder; optional --start). Windows: install.ps1 → %LOCALAPPDATA%\TwitchRecorder. Then pip install streamlink and start the helper. Check for updates still pulls from the public repo into the install dir.
Helper OGG output + Music only OGG (v6.27): helper streamlink recordings always write OGG audio (`audio_only` + `--ffmpeg-fout ogg` when ffmpeg is present → `~/TwitchRecordings/<user>-<weekday-stamp>.ogg`). No mp4 video container. Without ffmpeg, falls back to `.ts` only. Seamless join uses ffmpeg concat on `.ogg` segments. Music only / Demucs remux prefers sibling `<stem>-music.ogg` / `-vocals.ogg` (libvorbis, then libopus); falls back to `.wav` if ogg encode fails; still finds legacy `.mp3`/`.m4a`/`.wav`. Existing mp4/mp3 files on disk are unchanged — only new recordings/exports use ogg.
Demucs one-at-a-time queue (v6.28): Music only / Auto Music / Convert upload no longer spawn parallel demucs processes. Mid-stream finished segments still queue immediately, but demucs runs one job at a time (others stay Waiting…). Helper bar shows Music N running, M waiting. alreadyRunning / redo:false / natives-never-deleted unchanged.
Cancel waiting Music + orphan temp cleanup (v6.29): Waiting Music only / Auto Music / Convert jobs can be cancelled without killing the helper — per-row Cancel on History/Convert, plus Clear waiting Music on the helper bar when the demucs queue has waiters. POST /api/music-only/cancel accepts { "jobId" } or { "waiting": true }; running demucs is never SIGKILL'd (skipped). Cancelled jobs stay in /api/health musicJobs ~15 min like done/error. On helper startup (and once per diskWarn episode) orphan `music-only-*` temp dirs under ~/TwitchRecordings are removed, plus stale `seamless-*.txt` list files older than 1 hour; natives and -music/-vocals/-seamless exports are never touched. /api/health reports orphanTempsCleared / orphanTempsBytes for a one-shot UI flash.
